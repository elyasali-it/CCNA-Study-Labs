# Part XI: Network Architecture

## LAN Architecture

I know how to design a campus LAN using either a two-tier or three-tier model. In a two-tier design, also called a collapsed core, you have access switches connecting end-user devices and distribution switches connecting the access switches together. There's no separate core layer — the core function is collapsed into the distribution switches. In a three-tier design, you add a core layer whose only job is connecting the distribution switches to each other with fewer links and less delay.

Access switches sit at the edge of the network and connect directly to end-user devices. Their job includes providing physical ports, Power over Ethernet (PoE) for things like phones and access points, redundant uplinks to the distribution layer using EtherChannel (bundling multiple physical links into one logical link) and STP/RSTP (Spanning Tree Protocol, which prevents loops when there are redundant paths), and security features like port security, DHCP snooping, and Dynamic ARP Inspection.

Distribution switches connect the access switches to the rest of the network. They handle Layer 3 features like interVLAN routing, acting as the default gateway, and running First Hop Redundancy Protocols (FHRP) so if one distribution switch fails, another takes over. They also run dynamic routing protocols like OSPF, load balance traffic across redundant links, apply QoS, and filter traffic with ACLs.

Core switches, when present in a three-tier design, exist purely to connect distribution switches together as fast and reliably as possible. Their job is speed, high availability, and low latency — not running extra services.

I also know the topology terms used to describe these designs. A star topology is what you get when one device (like an access switch) has links radiating out to multiple other devices, similar to a child's drawing of a star. A full mesh means every device connects directly to every other device. A partial mesh means some devices connect directly but not all of them — this is common between distribution and core switches because a full mesh would use far more links and ports than needed. A hybrid topology combines both: for example, a star topology at the access layer paired with a partial mesh at the distribution layer, which is what most real networks look like.

For cabling, I know the standards that matter for a 100-meter UTP link at the access layer. 10BASE-T needs at least CAT3, 100BASE-T needs CAT5, 1000BASE-T needs CAT5E, and 10GBASE-T needs CAT6A (or CAT6 at a shorter 55-meter distance). I also know about multigig Ethernet — a newer standard from 2016 that lets you run 2.5 Gbps or 5 Gbps over existing CAT5E cabling, which matters when a wireless access point needs more than 1 Gbps but a full CAT6A cabling upgrade isn't worth the cost. For distribution and core links, fiber is usually the better choice, and I know the Optical Multimode (OM) categories — OM1 through OM4 — and how they affect maximum distance for standards like 1000BASE-SX and 10GBASE-SR.

I know what a small office/home office (SOHO) network looks like and how it differs from an enterprise LAN. A SOHO setup typically uses one consumer wireless router that internally acts as a switch, an access point, a router, and a firewall all in one box. The access point runs in autonomous mode, meaning it does all the work of managing the wireless network itself instead of relying on a separate wireless LAN controller.

I understand how Power over Ethernet works. A powered device (PD), like an IP phone or a camera, gets its DC power over the same Ethernet cable that carries data. The device supplying that power, usually the switch, is called power sourcing equipment (PSE). PoE works in two steps: power detection, where the switch sends a low-power signal to check if the connected device can actually accept PoE, and power classification, where the switch figures out how much power to supply, either through basic electrical signaling or by using LLDP or CDP messages for more precise negotiation. I know the standards too: PoE (802.3af) supplies up to 15 watts, PoE+ (802.3at) supplies up to 30 watts, and UPoE and UPoE+ (802.3bt) supply up to 60 and 90 watts.

## WAN Architecture

I know how Metro Ethernet (MetroE) works as a WAN service. The idea is that a service provider (SP) delivers what looks and acts like one big Ethernet switch connecting all of a company's sites, even though the SP's actual network in the middle stays hidden from the customer. Each site connects to the SP through an access link, and the point where the customer's device meets the SP's network is called the user network interface (UNI). The SP installs its switches at a facility called a point of presence (PoP), located as close to customer sites as possible.

I know the three Metro Ethernet service types defined by the MEF (Metro Ethernet Forum). E-Line is a point-to-point service, basically a private link between exactly two sites, similar in concept to a leased line. E-LAN is a full mesh service where every connected site can send frames directly to every other site, acting like one big LAN. E-Tree is a hub-and-spoke service where a central site can talk to all the remote sites, but the remote sites can't talk directly to each other.

This matters for IP routing too. With an E-Line, each point-to-point connection gets its own subnet, and only the two routers on that specific line become routing protocol neighbors. With an E-LAN, every connected router shares one subnet, and they all become neighbors with each other directly.

I understand Multiprotocol Label Switching (MPLS) at a conceptual level. Instead of just connecting sites with plain Ethernet, an MPLS provider builds one large internal network and uses MPLS VPNs to keep each customer's traffic and routes completely separate, even though many customers' traffic might be crossing the same physical devices. The customer's routers are called customer edge (CE) routers, and the provider's edge routers are called provider edge (PE) routers. Routing neighbor relationships form between CE and PE routers, not directly between CE routers at different sites. On the provider side, PE routers use a version of BGP called Multiprotocol BGP (MP-BGP) to exchange customer routes with each other, then redistribute those routes into whatever routing protocol the customer is using, like OSPF.

I also know the common ways businesses and consumers get Internet access, since these often become the WAN connection itself. DSL runs over existing phone lines, splitting voice and data at a device called a DSL access multiplexer (DSLAM) in the telco's central office. Cable Internet works similarly but rides on the cable TV company's coaxial cabling instead. Wireless WAN uses cellular technology — I know the difference between 4G LTE and the two flavors of 5G, standalone and non-standalone. Fiber Internet uses fiber-optic cabling run directly to the location and generally supports the fastest and longest-distance connections.

I understand how Internet VPNs secure a connection that runs over the public Internet instead of a private WAN. A VPN needs to deliver four things: confidentiality (encrypting the data so no one in the middle can read it), authentication (confirming the sender is who they claim to be), data integrity (confirming nothing was changed in transit), and anti-replay (stopping someone from capturing and resending a legitimate packet later). I know the difference between a site-to-site VPN, which is a permanent tunnel between two locations set up once by network engineers so end users never have to think about it, and a remote access VPN, which an individual device creates on demand, like an employee connecting from a coffee shop. IPsec is the most common framework for building these VPNs, and I know it uses two different modes depending on the situation: tunnel mode, which encrypts an entire original IP packet and is used for site-to-site VPNs, and transport mode, which encrypts only the data portion but not the original IP header, used for remote access VPNs. I also know that Transport Layer Security (TLS), the same protocol behind HTTPS, is a common alternative to IPsec for remote access, especially through tools like Cisco Secure Client.

## Cloud Architecture

I know the five characteristics that the National Institute of Standards and Technology (NIST) uses to define an actual cloud computing service, as opposed to just a virtualized data center. A service has to be on-demand self-service (the consumer requests it without waiting on a human), have broad network access (reachable from many device types over many kinds of networks), use resource pooling (the provider shares one pool of hardware capacity across all customers instead of dedicating specific servers), be rapidly elastic (it can scale up or down quickly and feel unlimited to the consumer), and be measured (usage gets tracked and billed accordingly).

I understand server virtualization at the level this matters for networking. A hypervisor is the software that manages a physical server's hardware and divides it among multiple virtual machines (VMs). Each VM gets its own slice of CPU (as virtual CPUs, or vCPUs), RAM, storage, and network access, and behaves as if it's running on its own dedicated physical server, even though it's actually sharing hardware with other VMs on the same host. On the networking side, each VM gets a virtual NIC (vNIC), and the server uses an internal virtual switch (vSwitch) to connect those vNICs to the server's physical NICs, which then connect out to the real physical network.

I also know how software containers differ from VMs. Containers hold an application plus everything it needs to run except the operating system, which makes them much smaller than a VM (megabytes instead of gigabytes) and much faster to start (seconds instead of minutes). Because containers don't include their own OS, they run through a container engine, software installed on top of a single shared host OS that starts, stops, and monitors containers. Docker is the tool most associated with popularizing containers, and Kubernetes is a common tool for managing large numbers of them.

I understand the difference between private cloud and public cloud. Private cloud, also called on-premise, means the cloud provider and the cloud consumer are part of the same company — an enterprise builds out its own virtualized data center to meet the NIST criteria for its own internal customers. Public cloud means the provider and consumer are different companies entirely, and the provider sells that same kind of service to many different customers.

I know the differences between the three most common cloud service categories. Infrastructure as a Service (IaaS) gives the consumer a VM with a chosen amount of CPU, RAM, and storage, and the consumer installs and manages the OS and applications themselves. Platform as a Service (PaaS) is aimed at developers and includes a prebuilt set of development tools on top of the VM, so a developer can focus on writing and testing code rather than managing servers. Software as a Service (SaaS) hands the consumer a fully working application with all the underlying VMs, OS, and infrastructure completely hidden — things like webmail or cloud file storage are common SaaS examples.

I know what Virtual Routing and Forwarding (VRF) is and why it matters in cloud environments. Normally a router has one routing table and won't allow two interfaces to sit on the same overlapping subnet. But in a cloud data center, multiple customers might use the exact same private IP ranges for their own VMs on the same shared physical server. VRF solves this by letting a single router maintain multiple separate virtual routing tables, one per customer, so the same subnet can exist twice on the same device without conflict. Each VRF gets its own routing table, its own routing protocol neighbor relationships, and its interfaces get assigned into the correct VRF through configuration.

I know the different WAN options for reaching a public cloud provider and the tradeoffs of each. Using a plain Internet connection is the fastest to set up but offers no privacy and no QoS guarantees. Adding a VPN over that Internet connection adds privacy but still no QoS. Using a private WAN like MPLS VPN or Ethernet WAN gives both privacy and QoS but takes longer to set up and costs more, and it makes it harder to migrate to a different cloud provider later since a new WAN connection has to be built each time. An intercloud exchange solves that last problem — it's a company that maintains private connections to multiple cloud providers at once, so a customer can connect once to the exchange and migrate between providers without installing a brand-new private WAN connection every time.

I understand how cloud-hosted routers get managed differently from a router sitting in a physical rack. A cloud router, like the Cisco 8000V, still runs Cisco IOS, but instead of a physical console cable, an engineer accesses it either through the hypervisor's virtual console (which behaves like plugging directly into the VM through a GUI) or through a serial console, which is reachable over telnet. Once the device is fully set up, SSH is the recommended method going forward since telnet sends everything in clear text. I also know the general advantages cloud management platforms provide over traditional device-by-device management: centralized visibility across every device from one dashboard, remote accessibility from anywhere, the ability to scale a deployment up or down quickly, automation for repetitive tasks, built-in security controls, and lower overall cost of ownership since less has to be run on-premise. Cisco's Meraki Dashboard is a real example of this model — a single web portal that shows live status, topology, and traffic path information across an entire managed network, with zero-touch provisioning that lets a device configure itself automatically the moment it's plugged in at a remote site.

## Troubleshooting Scenario

Say I'm brought in to look at a company that just moved one of its internal applications to a public cloud provider, and users at headquarters are complaining about slow performance and occasional connection drops when accessing it.

First, I'd check the WAN path. If the company connected to the cloud provider over a plain Internet connection, that alone would explain the intermittent performance problems, since a bare Internet connection provides no QoS guarantees and no SLA from the ISP for reaching that destination. I'd ask whether they added a VPN — encryption itself adds a small amount of overhead, so I'd want to know if that's contributing, but the bigger question is whether their Internet capacity can actually handle the extra traffic now that this application's data is crossing the WAN instead of staying inside the local network.

Next, I'd look at how HQ's own LAN is built, since a lot of egress traffic problems start closer to home. If HQ is running a two-tier design, I'd check whether the uplinks between the access switches serving the affected users and the distribution switches are actually load balancing properly across redundant paths, or if STP is blocking a link that should be active. I'd also confirm the distribution switches are handling QoS classification correctly on the way out to the WAN edge, since without a QoS trust boundary set correctly at the access layer, that traffic could be getting mismarked or deprioritized before it ever leaves the building.

Then I'd move to the cloud side. Since this is a public cloud deployment, I'd confirm whether the company set up VRFs correctly if any of the cloud VMs are sharing overlapping subnets with other customers on the same shared infrastructure — a routing table misconfiguration there could easily cause dropped or misrouted traffic that looks like a performance issue from the user's side. I'd also check whether the environment is properly elastic, meaning the resource pool is actually scaling to meet demand rather than the application hitting a capacity ceiling on the VM side.

Finally, I'd check the management visibility itself. If the environment uses something like the Meraki Dashboard or an equivalent cloud management platform, I'd pull up the topology and path visualization to look for interface errors, like CRC errors, high latency hops, or a device flagged as degraded, which would point me straight to the physical or logical point where things are breaking down rather than guessing across the whole path.
