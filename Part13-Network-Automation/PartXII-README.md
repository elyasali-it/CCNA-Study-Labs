# Part XII: Network Automation

This part covers four chapters: Introduction to Controller-Based Networking, Cisco Software-Defined Access, Understanding REST and JSON, and Understanding Ansible and Terraform.

## Controller-Based Networking

Every networking device does its work in three planes. The data plane is the actual job of moving traffic — a switch matching a frame's destination MAC address and sending it out a port, a router matching a packet's destination IP address and forwarding it, adding or stripping a VPN header, applying an ACL. The control plane is whatever builds and maintains the tables the data plane uses to make those decisions — OSPF building the IP routing table, a switch learning MAC addresses, STP blocking a port. The management plane is the layer above both of those — Telnet, SSH, SNMP, syslog — protocols that let me as an engineer manage the device, but that don't directly feed the forwarding decision.

Traditional networks run both the control plane and the data plane locally on every device, which is called a distributed control plane. Each router runs its own copy of OSPF and talks to its neighbors to build its own routing table. Software-Defined Networking (SDN) changes that by introducing a controller — a piece of software, usually running on a server or VM, that centralizes some or all of that control plane logic instead of leaving it distributed across every box. A network built this way still forwards frames and packets exactly like before; what changes is where the intelligence that builds the forwarding tables lives.

Inside a switch, the data plane isn't run by a general CPU because that would be too slow for the volume of traffic involved. As an example, a 24-port switch running all ports at 1 Gbps full duplex, with 125-byte frames, needs to process roughly 24 million frames per second. That kind of speed comes from an ASIC (a purpose-built chip) paired with TCAM (a type of memory built for fast table lookups), while the CPU and RAM handle IOS and the control/management plane work.

A controller talks to the devices below it through a southbound interface (SBI) and exposes its own data and functions to other software through a northbound interface (NBI). The SBI is often built on an API — a way for one program to exchange data with another, as opposed to a protocol, which is a document defining rules. A REST API (REpresentational State Transfer) is one common style of API for this. In a REST exchange, a client sends an HTTP GET request to a URI on the controller, and the controller answers with structured data, usually formatted as JSON. Because the NBI is what other applications use to pull data from the controller and push configuration into it, it's the piece that actually enables network programmability.

Cisco built two intent-based SDN products that show two different points on the centralization spectrum. Cisco ACI (Application Centric Infrastructure) is Cisco's data center SDN offering. It uses a spine-leaf physical design — every leaf switch connects to every spine switch, leaf switches never connect to each other, spine switches never connect to each other, and all endpoints (servers, VMs, other network devices) connect only to leaf switches, never to spine switches. ACI is controlled by the APIC (Application Policy Infrastructure Controller), which pushes control-plane logic down to the switches using a protocol called OpFlex. Instead of configuring VLANs, trunks, and ACLs port by port, an engineer defines endpoint groups (EPGs) and policies describing which groups can talk to which, and the APIC translates that intent into the actual switch configuration.

The two SDN examples in this material — OpenFlow/OpenDaylight and Cisco ACI — differ in how centralized their control plane is. OpenFlow centralizes control mostly completely, while ACI is described as partially centralized, since the switches still keep some control-plane function locally even while the APIC drives the intent-based policy layer.

Comparing traditional and controller-based networking comes down to two exam-relevant ideas: how automation changes network management, and how controller-based architecture compares to the traditional per-device model. With a controller and its northbound API, I can pull structured data — like the trunk configuration and operational state of an interface — as a ready-to-use Python dictionary instead of parsing raw `show` command text. That data model is what makes automation practical: scripts don't have to scrape CLI output, they call an API and get variables back. The result is that I don't have to think through every command on every device individually — the controller applies consistent, streamlined settings, and changes tend to be faster and produce fewer errors.

## Cisco Software-Defined Access

Cisco SD-Access (Cisco SD-Access) is Cisco's software-defined approach to campus wired and wireless LANs. The word "access" in the name refers to the access layer of a traditional core/distribution/access design — that's the layer where endpoints connect in.

SD-Access builds its fabric out of two layers working together:

- **Underlay:** the physical switches, routers, cabling, and wireless gear, along with the IP addressing and routing that lets every SD-Access device reach every other SD-Access device. The underlay's whole job is to support VXLAN tunnels running on top of it.
- **Overlay:** the collection of devices using VXLAN tunnels to move traffic between endpoints across the fabric.

VXLAN (Virtual eXtensible Local-Area Network) is the tunneling technology SD-Access uses to build the overlay. It encapsulates the entire original Ethernet frame — not just the IP packet — inside a new IP/UDP/VXLAN header, which lets SD-Access forward both Layer 2 and Layer 3 traffic through the tunnel. The switch that first receives a frame and encapsulates it is the ingress fabric edge node; the switch that strips the VXLAN header at the far end is the egress fabric edge node. Fabric edge nodes are the equivalent of a traditional access layer switch — they connect endpoints. A fabric border node connects to devices outside SD-Access, like WAN routers or another data center fabric. A fabric control-plane node runs LISP and handles endpoint lookups for the fabric.

Because the underlay is its own separate IP address space from the enterprise address space used by the overlay, SD-Access needs a way to know which fabric edge node currently owns a given endpoint. That's what LISP (Locator/ID Separation Protocol) does. Each fabric edge node registers the subnets or endpoints it can reach — called endpoint identifiers (EIDs) — along with its own underlay IP address, called a routing locator (RLOC), with a LISP map server. When an ingress fabric edge node gets a frame for a destination it doesn't recognize, it asks the LISP map server which RLOC can reach that EID, the map server confirms with that node, and the ingress node then knows which VXLAN tunnel to use. This is the mechanism behind SD-Access's host mobility use case: when a user moves their laptop to a different part of the building and connects to a different fabric edge node, that node registers the updated location with the map server, so traffic keeps reaching them without the user having to be moved to a different VLAN or subnet.

Cisco Catalyst Center (previously named Cisco DNA Center) is the controller for SD-Access. It plays two roles: it's the SDN controller for SD-Access fabrics specifically, and it's also a general network management platform (NMS) that can manage traditional, non-fabric devices. As a controller, Catalyst Center configures the underlay automatically in a greenfield deployment — all switches become Layer 3 devices, IS-IS runs as the underlay routing protocol, all inter-switch links become routed Layer 3 links instead of traditional Layer 2 trunks, and STP/RSTP is no longer needed because there are no Layer 2 loops to block. The fabric edge node itself becomes the default gateway for endpoints, replacing the traditional HSRP/FHRP setup on a pair of distribution switches.

SD-Access replaces traditional IP-based ACL security with a group-based model. Each endpoint gets classified into a scalable group, and each scalable group gets a scalable group tag (SGT). Policy is then defined between groups — for example, "guests can't reach the internal employee group" — rather than as a growing, hard-to-audit list of ACL entries tied to specific IP subnets. When a new endpoint sends its first packet, the ingress fabric edge node checks with Catalyst Center (which coordinates with an identity system like Cisco ISE to figure out which SGT the endpoint belongs to), and if policy allows communication between the source and destination SGTs, Catalyst Center has the edge nodes build the VXLAN tunnel; if policy doesn't allow it, the tunnel is never built and the traffic never flows.

As a general management platform, Catalyst Center covers the usual NMS functions — single pane of glass, device discovery and topology mapping, lifecycle management across day 0 (install), day 1 (initial config), and day n (ongoing monitoring) — plus features that go further than a typical NMS, like path trace (showing the actual forwarding path between a source and destination, including which ACLs are in that path and whether they'd permit or deny), Software Image Management for automating OS upgrades, and Plug-and-Play zero-touch provisioning for new devices.

One exam-relevant topic that shows up here is AI and machine learning in network operations. Narrow AI is designed for a specific, limited task — voice assistants, image recognition, that kind of thing. Generative AI can learn, be taught, and produce new output based on patterns and experience, with ChatGPT as the common example. Machine learning is the branch of AI focused on building models from data so a system can improve its own predictions over time without being explicitly reprogrammed for each new case. In network operations, this shows up as AI Ops — using AI/ML to automate routine tasks, monitor for anomalies, predict problems before they cause an outage, and speed up root cause analysis. A generative AI tool can also be genuinely useful for learning the material itself — asking it to summarize a set of subnets into an access list, for instance — but the output still has to be checked, since it isn't always accurate or efficient, and using it for actual production changes without validating it first is how avoidable mistakes get made.

## REST APIs and JSON

A REST API follows a client/server model. My application (the REST client) sends a request to a REST server — some other application that owns the resource I want. The server processes that request and sends back a response with the data I asked for. REST is also stateless, meaning the server doesn't remember anything about my previous requests; every request has to carry everything needed to process it on its own. And REST resources are marked as cacheable or not, so a client knows whether it's safe to reuse a previous response instead of asking again.

Software actions map to a well-known acronym: CRUD, for Create, Read, Update, and Delete. REST APIs typically ride on HTTP, and HTTP verbs map onto those same CRUD actions — POST for create, GET for read, PATCH or PUT for update, and DELETE for delete. So a REST client asking a controller for a list of devices sends an HTTP GET; a REST client telling the controller to build a new policy sends an HTTP POST.

Every REST API call targets a specific resource, identified by a URI. Take this example: `https://dnac.example.com/dna/intent/api/v1/network-device?parm1=10.1.1.1`. The scheme (`https://`) identifies the protocol. The authority (`dnac.example.com`) identifies the host. The path (`/dna/intent/api/v1/network-device`) identifies the resource itself — in this case, the list of network devices. And the query (`?parm1=10.1.1.1`) passes a parameter that narrows the request down to a specific value.

Before making calls to something like Cisco Catalyst Center, I have to authenticate. That's typically done with an HTTP POST to an authentication endpoint using basic auth (username and password), which returns a token — in Catalyst Center's case, valid for one hour. From then on, every subsequent API call has to include that token in an HTTP header called X-Auth-Token. Postman is a common tool for working through this manually before writing it into a script — I configure the authentication call, get the token back, plug it into the header field for the next call, and then issue the actual GET request against a resource like the network device inventory.

Once I get data back from a REST call, it needs a format both the sender and receiver understand — that's what a data serialization language does: it defines how to represent variables and data structures as plain text so they can move across a network or get stored in a file. JSON (JavaScript Object Notation) is the one the CCNA blueprint focuses on, and it's genuinely the easiest of the common options to hand-read. A JSON object is a set of key:value pairs enclosed in curly brackets. The key is text in double quotes, before a colon; the value comes after the colon and can be text (in double quotes), a number (no quotes), an array, or another JSON object. Multiple pairs are separated by commas, except after the last one. A JSON array is a list of values enclosed in square brackets, and it can be used as the value in a key:value pair — which is how JSON nests, with objects containing arrays and arrays containing objects.

XML (eXtensible Markup Language) does the same basic job as JSON but with a different look — every variable gets an opening and closing tag, like `<macAddress>f8:7b:20:67:62:80</macAddress>`, which trades away some human readability for structure. YAML (YAML Ain't Markup Language) goes the opposite direction, aiming to be the cleanest and most human-readable of the three; Ansible relies heavily on YAML for its variable files.

## Ansible and Terraform

The traditional way to change a device's configuration is to log in, enter configuration mode, type commands, and save the running-config to startup-config. That works fine for one engineer managing a handful of devices, but it breaks down at scale.

The core problem this creates is configuration drift — a device's configuration changing over time until it no longer matches what it's supposed to be. Picture two network engineers, each with years of experience, who both get called in overnight to fix separate issues on separate branch routers. Each makes a small config change to resolve their issue, documents it properly in the change management system afterward, and life goes on. Months later, the branch routers that were supposed to be running an identical standard configuration now have small, undocumented differences between them, and neither engineer remembers making the original change. That's configuration drift, and manual per-device configuration has no built-in way to prevent it or even flag when it's happened.

The first step toward fixing that is storing configuration files centrally instead of leaving them scattered per-device, ideally under version control. A tool like Git, paired with a service like GitHub, tracks exactly who changed what, when, and shows a line-by-line diff between versions — solving the "who changed what and when" problem that manual configuration can't answer on its own. Beyond just storage, a configuration management tool can actively compare a device's running configuration against the ideal configuration stored centrally, flag any difference as drift, and either notify staff or automatically correct it — that ongoing comparison is called configuration monitoring or configuration enforcement. Separately, configuration provisioning is what actually pushes an approved change from the central config file out to the device.

A configuration management tool typically separates a device's configuration into two pieces: a template, which represents everything common to all devices playing the same role, and variables, which capture the handful of values unique to one specific device — hostname, IP addresses, a router ID. The tool then combines a template with a device's variable file to produce that device's actual configuration. Ansible uses the Jinja2 language for templates, with variable names inside double curly brackets like `{{hostname}}`, and uses YAML to define the values that get substituted in. This separation matters for a few concrete reasons: it keeps devices from becoming "snowflakes" with one-off configurations nobody remembers the reason for, it makes deploying a new device in an existing role as simple as copying an existing variable file and changing a few values, and it makes troubleshooting easier because a problem affecting every device with a given role points straight at the shared template, while a problem on a single device points at that device's variable file.

Ansible itself uses an agentless architecture — it doesn't require any special software running on the managed device. Instead, it connects using protocols the device already supports, typically SSH or NETCONF, and does the work the same way a human logging in and typing commands would. By default, Ansible uses a push model: an engineer builds a playbook (the file defining what actions Ansible should take and under what logic) along with an inventory file (which lists the devices, grouped by role, that the playbook can target), and Ansible pushes the resulting configuration out to the target devices over SSH. A pull model is also possible using a separate tool called Ansible-pull, but push is the default.

Terraform, from HashiCorp, is an infrastructure as code (IaC) tool. Where Ansible is generally the better fit for configuring existing network devices, Terraform is more commonly used for provisioning infrastructure itself — creating and managing cloud or on-premises resources like virtual machines, storage, and networking components, including services from providers like AWS, Azure, and Google Cloud. Terraform uses its own language, HashiCorp Configuration Language (HCL), which like Ansible's YAML is meant to be human-readable. Its core building blocks are configuration files (the desired end state), providers (plugins that let Terraform talk to a specific platform like AWS or Azure), resources (the actual things being created or managed, like a VM), data sources (references to infrastructure that already exists outside Terraform's control), variables (for reusable, flexible configuration), state files (Terraform's record of the current state of everything it manages, used to detect what's changed), and modules (reusable, packaged sets of resources and configuration). Terraform's workflow runs in three stages: write the configuration, generate a plan describing exactly what will be created, changed, or destroyed, and then apply that plan once it's been reviewed.

Choosing between them comes down to what I'm trying to accomplish. If a team is already fluent in the CLI and wants to automate device configuration across a fleet of similar devices, Ansible's playbook style maps naturally onto that. If the goal is leading with infrastructure as code, doing more advanced provisioning across cloud and on-prem, or tracking infrastructure state over time, Terraform tends to be the better fit. It's common enough for both to be used together, each covering the part of the job it's built for.

## Troubleshooting Scenario

A network team decides to move a branch office from a traditional access layer design to Cisco SD-Access, and to automate the ongoing configuration of the new fabric switches with Ansible instead of manual CLI changes. A few weeks after the cutover, a user working from a laptop reports they can reach internal file shares from the main office but lose access the moment they walk over to a conference room and reconnect on a different jack.

I start at the SD-Access layer, since the deployment just changed. The user moving between jacks and losing access to specific resources — not the whole network — points at how the fabric locates that endpoint rather than a straightforward Layer 2/3 outage. I check the LISP map server for the user's current EID-to-RLOC mapping. If the new fabric edge node the laptop reconnected through never registered the updated location, the ingress node handling return traffic would still be forwarding to the old RLOC, which matches the symptom exactly. I also check the SGT assigned to this user's identity through Catalyst Center's policy integration, since a mismatch between the group the user gets classified into at the new jack versus the old one could explain the file share access getting blocked even with a correct RLOC — the fabric would simply decline to build the tunnel if policy between that SGT and the file server's SGT denies it.

Once I confirm which of those two it is, I trace the fix back through the automation layer that put the fabric there in the first place. If the branch's fabric edge switches were provisioned from an Ansible playbook and variable files, I check whether the variable file for the new switch actually matches its intended role and whether Catalyst Center's automatic underlay provisioning completed cleanly on that device, rather than assuming the issue is purely a runtime LISP or policy problem. A gap in the variable file at provisioning time is exactly the kind of thing that would silently produce a device that looks fine at the CLI but behaves inconsistently with the rest of the fabric.
