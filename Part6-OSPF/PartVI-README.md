# Part VI: OSPF

Everything before this point in my notes was about getting packets onto the right subnet. This part is about how routers actually learn which subnets exist in the first place and pick the best way to get there. Cisco only puts one routing protocol on the CCNA blueprint, and it's OSPF, so this whole part is really one long study of a single protocol from the ground up.

## Why routers need a routing protocol at all

A router builds its routing table from three sources: connected routes, static routes, and dynamic routing protocols. Static routes work fine for a two-router network. They fall apart the moment you have a real internetwork, because every time a subnet changes, someone has to go update every router by hand. A routing protocol solves that by having routers talk to each other, advertise what they know, and pick the best route to each subnet automatically. When the topology changes, the routers figure it out and reconverge without a human touching the CLI.

Routing protocols do four jobs: learn about subnets from neighbors, advertise what they know back out, pick the best route when more than one exists using a metric, and detect and react to failures (convergence). OSPF is a link-state protocol, which puts it in a different family than something like RIP. RIP is distance vector — routers only tell each other "I can reach this subnet in X hops," and each router trusts its neighbor's math without seeing the actual topology. OSPF instead floods detailed information about every link and router in the area, so every router ends up with an identical map of the network and calculates routes independently using the same math (Dijkstra's SPF algorithm). That's the trade — link-state costs more CPU and memory than distance vector, but it converges faster and doesn't have the loop problems that plagued old RIP networks.

OSPF's metric is cost, which is based on interface bandwidth by default, not hop count. That matters in practice: a route with fewer hops isn't automatically the best route in OSPF the way it would be in RIP. A one-hop path over a slow serial link can lose to a two-hop path over Gigabit Ethernet, because OSPF is adding up the cost of every outgoing interface along the path, and cost is inversely related to bandwidth. I like this because it actually reflects reality on an MSP network — a "shorter" path over an ancient WAN circuit isn't necessarily faster.

## Becoming neighbors and building the map

Two routers on the same subnet don't automatically become OSPF neighbors just because OSPF is enabled. They send Hello packets to the multicast address 224.0.0.5 to discover each other, and both sides have to agree on a set of settings before the relationship is allowed to form — same area, same subnet, matching Hello and Dead timers, and a couple of other things I'll get into further down. If everything lines up, the two routers move through a sequence of states: down, init (I've heard from you but you haven't heard from me), 2-way (we've both heard each other), and then — if the link needs it — exchange and loading while they trade their full link-state databases, ending at full. Full means both routers have identical copies of each other's LSAs and are ready to run SPF.

On point-to-point links, every neighbor relationship goes all the way to full. On Ethernet-style broadcast segments with more than two routers, OSPF elects a designated router (DR) and a backup designated router (BDR) so that not every router has to exchange its database with every other router — that would be a lot of redundant chatter. Instead, everyone syncs through the DR, and the DR relays it to everyone else. Routers that aren't the DR or BDR are called DROthers, and they only reach a 2-way state with each other, while still reaching full with the DR and BDR. This is something that tripped me up at first — seeing a neighbor stuck at 2WAY/DROTHER in the output isn't automatically a problem, it's expected behavior on a broadcast segment.

DR/BDR election uses OSPF priority first (highest wins, default is 1, and setting priority to 0 takes a router out of the running entirely), and falls back to router ID if priority ties. Critically, this election doesn't preempt. If a router with a higher priority shows up after a DR is already elected, it doesn't take over — the existing DR keeps the job until it actually fails. That's different from how Spanning Tree elects a root bridge, where a superior bridge ID does take over immediately. I had to unlearn my STP instincts here.

## Network types and why they matter for troubleshooting

OSPF behaves differently depending on the network type configured on the interface, and this is one of those settings that's easy to overlook until it breaks something. The two types on the CCNA blueprint are broadcast (the default on Ethernet, dynamically discovers neighbors, uses a DR/BDR) and point-to-point (also dynamically discovers neighbors, but skips DR/BDR election entirely, since there's only ever two routers on the link anyway). If you're using an Ethernet segment purely as a point-to-point WAN link between two routers, it makes sense to set it to `ip ospf network point-to-point`, because there's no reason to burn a DR/BDR election on a link that only ever has two routers.

The failure mode I want to remember here is subtle: if one end of a link is set to broadcast and the other end is point-to-point, the two routers will still become full neighbors and exchange their LSDBs successfully. Everything looks healthy in `show ip ospf neighbor`. But neither router will actually add routes learned from that neighbor into its routing table, because the LSAs generated under each network type carry different details, and SPF can't reconcile them. That's a nasty one to troubleshoot precisely because the neighbor relationship looks fine — you have to think to check the network type specifically.

## Configuring OSPF: two ways to enable it

There are two configuration styles and I want to know both, because I'll run into legacy configs using the old style constantly in the field.

The traditional way uses the `network` command inside `router ospf` mode, matching interfaces by IP address and wildcard mask, then assigning them to an area. The wildcard mask logic is the same as an ACL wildcard — a 0 in an octet means "match exactly," a 255 means "ignore this octet." You can write one broad network command that sweeps in every interface on the router, or several narrow ones that each match a single interface. Either way works, and IOS just enables OSPF on whatever interfaces match, using the area specified in that particular network statement.

The newer style skips the network command and uses `ip ospf process-id area area-id` directly under the interface. It's more explicit — no wildcard math, no guessing which interfaces a broad network command might sweep in accidentally. I actually prefer this style for anything I'd hand off to a junior tech, because there's zero ambiguity about what's enabled where. The two styles can coexist on the same router, and if a network command and an interface subcommand both try to place the same interface in different areas, IOS goes with whichever came later in the config.

Either way, once OSPF is configured, `show ip ospf neighbor`, `show ip ospf database`, and `show ip route ospf` are the three commands that map to the three things OSPF actually does — discover neighbors, exchange the LSDB, and calculate routes. If neighbors aren't showing up, that's a Hello/discovery problem. If neighbors are full but routes are missing, that's usually a network type or area mismatch, not a Hello problem.

## Router ID, and why I always set it manually

The OSPF router ID is a 32-bit number that uniquely identifies each router in the OSPF domain, and by default IOS picks it automatically — first checking for a manually configured `router-id`, then falling back to the highest IP address among any up loopback interfaces, then the highest IP address among any other up interface. That auto-selection is exactly the kind of thing that seems harmless until a router reloads, picks a different physical interface as its highest IP, and its RID silently changes. Neighbor relationships break, the neighbor table clears, routes drop out, and nobody touched the config. I'm going to make a habit of setting `router-id` explicitly on every router I deploy, specifically to avoid chasing a ghost problem that's really just IOS re-picking an interface after a reboot.

## The optional settings that actually get used in production

A few features that aren't strictly required for OSPF to function, but that I'd expect to see configured on any real network:

**Passive interfaces.** If a LAN interface has no other OSPF routers on it — just end-user devices — there's no reason to send Hello packets out that interface. `passive-interface` stops OSPF from trying to form neighbors there while still advertising the connected subnet into OSPF. On a router with a lot of interfaces, it's usually cleaner to set `passive-interface default` and then explicitly un-passive the handful of interfaces that actually face other routers, rather than passive-ing each LAN interface one at a time.

**Default routes.** For internet-facing routers, you don't want every router in the company learning specific routes for the entire internet — you want one router with a default route to the ISP, and everyone else learning a default route through OSPF that points back to that router. `default-information originate` does this, with an `always` option to keep advertising the default even if the local static default route disappears temporarily.

**Cost tuning.** Cost defaults to a formula of reference bandwidth divided by interface bandwidth, and the classic gotcha is that the default reference bandwidth (100 Mbps) makes Fast Ethernet, Gigabit, and 10-Gig links all tie at a cost of 1, because the formula floors out. On any network with faster-than-Fast-Ethernet links, that's a real problem — OSPF can't tell a 1-Gig path from a 10-Gig path. The fix is `auto-cost reference-bandwidth`, bumped up to a value higher than the fastest link in the network, on every router in the OSPF domain consistently.

**Hello and Dead intervals.** These have to match between neighbors or they won't form a relationship — that's a Table 24-2 requirement, not optional. Defaults are 10 seconds Hello / 40 seconds Dead on broadcast interfaces, a 4-to-1 ratio. You can tighten this for faster failure detection, but both sides have to agree, and IOS won't stop you from configuring something dumb like a Dead interval shorter than the Hello interval — which would mean the neighbor relationship times out before a single Hello has a chance to arrive.

## When two routers become neighbors but nothing gets learned

This is a category of problem that's worth calling out on its own, because it's the sneaky one. Some misconfigurations stop neighbors from forming at all — mismatched areas, mismatched Hello/Dead timers, a duplicate router ID — and those are relatively easy to spot because the neighbor table is just empty or missing an entry. But three other misconfigurations let the neighbor relationship form successfully while quietly preventing routes from being learned: mismatched MTU, mismatched network type, and both neighbors on a segment using OSPF priority 0. In the priority-0 case specifically, the routers all sit at 2WAY/DROTHER indefinitely because nobody is willing to be the DR, and the symptom is a stable-looking neighbor table that just never reaches full on that segment.

The lesson I'm taking from this: a healthy-looking neighbor table isn't proof that OSPF is actually forwarding traffic correctly. I need to check `show ip route ospf` too, and if routes are missing despite full neighbors, go look at MTU, network type, and priority before I start doubting the area design.

## Areas: why bother with more than one

A single-area design (everything in area 0) works fine for small to medium networks and is honestly all the CCNA blueprint expects. But the reason multiarea OSPF exists is CPU and memory — every router inside an area has to hold detailed link-state information about every router and link in that area, and SPF has to chew through all of it whenever anything changes. Split a large network into multiple areas, and each internal router only needs the detailed topology for its own area, plus summarized subnet information (Type 3 LSAs) for everything in other areas. Changes inside one area only trigger SPF recalculation for routers in that area, not the whole domain. Every non-backbone area has to connect back to area 0 through at least one Area Border Router, and area 0 itself is the only area allowed to touch every other area directly — no area-to-area shortcuts.

## Administrative distance and picking between competing sources

Metrics only help a router choose between multiple routes learned by the *same* protocol. When one router learns a route to the same subnet from two different protocols — say OSPF and EIGRP — the metrics aren't even comparable (OSPF cost and EIGRP's composite metric use completely different math), so IOS falls back to administrative distance, essentially "how much do I trust this source." Connected routes sit at 0, static at 1, EIGRP internal at 90, OSPF at 110, RIP at 120 — lower always wins regardless of what the metric says. This only comes up on routers running more than one routing source for the same subnet, which happens more than you'd think — a router with both a static route and a dynamic protocol pointed at the same destination, or a network in the middle of a merger running two protocols during a migration.

When multiple routes to the *same* subnet from the *same* protocol tie on metric, OSPF adds all of them to the routing table as equal-cost multipath routes, and the router load-balances per destination address rather than per packet, to avoid the overhead of juggling packet order.

## Longest prefix match — the rule that actually decides forwarding

This is the part of OSPF study that isn't really OSPF-specific at all — it's how every router decides which route to use once the table is built, and it applies just as much to static and connected routes. When a packet's destination matches more than one route in the table because the subnets overlap (say a /16 summary, a /23, and a /26, all covering the same address), the router doesn't care about administrative distance or metric at that point. It picks whichever matching route has the longest prefix — the most specific mask. A /32 host route always wins over anything broader if it matches, because there's nothing more specific than an exact address match.

**Troubleshooting scenario: neighbors up, routes missing, and a branch that won't reach anything**

Picture a client site with three routers in a hub-and-spoke design — R1 at the hub, R2 and R3 as branch routers connected over what used to be point-to-point serial links, now migrated to Ethernet WAN. Everything's in area 0. A tech doing the migration configured R1's side of the R1–R2 link with `ip ospf network point-to-point` to mimic the old serial behavior, but left R2's side on the Ethernet default of broadcast. Meanwhile, over on the R1–R3 link, someone set an MTU of 1600 on R1's interface during a separate troubleshooting session months ago and forgot to revert it, while R3 still sits on the default 1500.

The ticket comes in as "branch office can't reach anything on the network." First move: `show ip ospf neighbor` on R1. Both R2 and R3 show up, both at FULL. That rules out the obvious stuff — no area mismatch, no RID collision, no Hello/Dead mismatch, otherwise they wouldn't even be neighbors. So the temptation is to say OSPF's fine and go look somewhere else. Instead, I'd check `show ip route ospf` on R1 next, and find it's missing routes to subnets behind R2 and R3 entirely, despite both neighbors showing full.

That combination — full neighbors, missing routes — points straight at the two misconfigurations that let neighbors form while blocking route exchange. For R2, `show ip ospf interface` on both ends shows R1 reporting "Network Type Point-to-Point" and R2 reporting "Network Type Broadcast." Fix is matching the network type on both ends. For R3, same command shows the MTU mismatch buried in the interface output — R1's database exchange with R3 never actually completes cleanly even though the neighbor state reports full, because the two sides can't agree on how big a packet they can send during the exchange. Fix is bringing R1's MTU back to 1500 to match R3, or explicitly setting `ip mtu` to match on both sides if the 1600 setting was actually intentional for another reason.

Once both are corrected, SPF reruns, the LSDBs actually reconcile, and the branch routes populate on R1. The takeaway I keep coming back to: a full neighbor state tells me discovery and adjacency worked. It tells me nothing about whether the two ends agree on the details that let SPF actually build routes from what they exchanged.
